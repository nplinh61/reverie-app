
# ADR-002: Use Spring Data JDBC for Domain Persistence

- Status: Accepted
- Date: 2026-11-19
- Decision makers: Product owner and development team

## Context

Milestone 0 used plain Spring JDBC with no domain tables. Milestone 1 introduces
the first domain model (users, profiles, spaces, memberships, invitations, and
email verification tokens) and needs a persistence approach.

The backend is a modular monolith maintained by a single developer, so simplicity
and explicit behavior matter. PostgreSQL remains the source of truth, and Flyway
manages the schema.

## Decision

Use Spring Data JDBC.

- The schema is defined first through Flyway migrations. Entities map to existing
  tables; the framework does not generate or migrate the schema.
- Each table maps to a small aggregate root. For Milestone 1 the roots are User,
  Profile, Space, SpaceMember, Invitation, InvitationAcceptance, and
  EmailVerificationToken. No aggregate nests another aggregate. References between
  aggregates are stored as plain UUID columns.
- Complex membership, authorization, and invitation operations use explicit SQL
  through JdbcClient or JdbcTemplate rather than derived repository methods.
- Primary keys are UUID values generated by the application. Entities implement
  Persistable<UUID> with a transient new-state flag so Spring Data JDBC can tell
  an insert from an update. An application-assigned id is never null, so the
  default null-id check cannot be used.
- Optimistic locking with @Version is not used in Milestone 1. Concurrency safety
  for invitation usage limits is provided by conditional SQL and database
  constraints instead (see ADR-004).

## Alternatives Considered

### Spring Data JPA and Hibernate

Advantages: rich mapping, relationships, lazy loading, large ecosystem.

Disadvantages: implicit flushing, lazy-loading surprises, a persistence context
and entity lifecycle that add conceptual load, and object-graph behavior that can
hide the SQL actually run. This is more than the MVP needs.

### Plain Spring JDBC only

Advantages: no new dependency, full control.

Disadvantages: repetitive row mapping and boilerplate for simple reads and
writes, with no repository abstraction for the common cases.

## Consequences

Positive:
- Schema-first development keeps PostgreSQL authoritative and matches the Flyway
  workflow.
- Small aggregates with id-only references keep saves predictable and avoid
  loading large object graphs on the authentication and authorization hot paths.
- Explicit SQL is available exactly where the logic is non-trivial.

Negative:
- Application-assigned UUIDs require the Persistable new-state pattern, which is a
  small amount of boilerplate, reduced by a shared base type.
- Mapping richer relationships later may require more manual work than JPA would.

## Reconsideration Conditions

Reconsider if the domain develops relationship graphs or query needs that make
explicit SQL and small aggregates materially harder to maintain than a full ORM.
